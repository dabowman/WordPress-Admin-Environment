# Parity: Users (core:users)

> Audited 2026-05-29 against WordPress 7.0 core. Shell app: `src/apps/users/`. Classic counterpart: `wp-admin/users.php`, `wp-admin/user-new.php`, `wp-admin/includes/class-wp-users-list-table.php` (Edit User boundary: `wp-admin/user-edit.php`, mostly owned by the `core:profile` audit).

## Verdict

**Major gaps.** `core:users` is a thin DataViews list with exactly one action: permanent bulk delete-and-reassign-to-self. It does that one thing carefully (self-delete guard, `force: true`, `reassign`). But it ships *none* of the other first-class actions the classic Users screen offers — no add-user, no edit/row navigation, no "Change role to…" bulk dropdown, no "Send password reset", no per-user post count, no "View posts" link, no avatar, and no real role-tab strip (role counts ride the filter dropdown instead). Several of those are pure shell-side work the current REST surface fully supports (add-user via `POST /wp/v2/users`, bulk role change via per-user `PUT` with `{id, roles}`, avatar via `avatar_urls`, multi-role filter via `?roles=a,b`). A smaller set is genuinely blocked by the absence of REST surfaces: **Send password reset** (no `retrieve_password` REST endpoint), **sort by Username/login** (not in the REST `orderby` enum), **per-user post count** (`count_users`/`count_many_users_posts` are PHP-only), the **welcome-email toggle** (`send_user_notification` not in the REST schema), and the entire **multisite invite / Add-Existing-User / Remove** family (internal functions, plus DELETE returns 501 on multisite). The delete reassign UX is also a functional divergence: classic lets you pick *any* target user or "delete all content"; the shell hard-codes reassign-to-the-acting-user with no chooser.

## Counterpart mapping

- **Classic screen(s):**
  - List: `wp-admin/users.php` (action switch + render) powered by `WP_Users_List_Table` (`wp-admin/includes/class-wp-users-list-table.php`).
  - Add New / Add Existing: `wp-admin/user-new.php` (single-site `createuser` via `edit_user()`; multisite `adduser`/invite via `add_existing_user_to_blog` / `wpmu_signup_user`).
  - Edit another user: `wp-admin/user-edit.php` (the `core:profile` audit owns the form; the **only** entry point on the list screen is the username/Edit row link, which `core:users` does not render).
- **REST / core-data surface the shell uses:**
  - `useEntityRecords('root', 'user', queryArgs)` with `context: 'edit'` → `GET /wp/v2/users` (`WP_REST_Users_Controller::get_items`). `src/apps/users/index.js:108`.
  - `deleteEntityRecord('root', 'user', id, { force: true, reassign })` → `DELETE /wp/v2/users/{id}` (`WP_REST_Users_Controller::delete_item`). `src/apps/users/index.js:206`.
  - Per-role counts: `useEntityElementCounts('root','user','roles', roleValues)` → one `GET /wp/v2/users?roles={r}&per_page=1&_fields=id&context=edit` per role, reading `X-WP-Total`. `src/apps/users/index.js:125` + `src/apps/_shared/dataviews/useEntityElementCounts.js`.
  - Acting-user id from `window.wpAdminShell.userId` (PHP-injected). `src/apps/users/index.js:165`.
  - Resolved DataView doc via `useDataView(screenId)` (baseline ships in `app.json#dataView`, injected post-merge). `src/apps/users/index.js:77`.
- **Project screen spec:** `docs/screens/users.md` (49 KB; covers list + new + edit + profile + application-passwords as one cluster). Present and thorough — explicitly catalogs the REST gaps this audit re-verified.

## Functional divergences

Behaviors present in BOTH but implemented differently.

1. **Delete reassignment target is hard-coded, no chooser.**
   Classic presents a fieldset: *Delete all content* (radio) vs *Attribute all content to:* with a `wp_dropdown_users()` of every other user (`users.php:416-435`). The user picks the destination. The shell hard-codes `reassign: currentUserId` (`src/apps/users/index.js:208`) — content always lands on the acting user, with no option to delete content outright or assign it to a third party. The REST endpoint supports both modes (`reassign=ID` and `reassign=false`→delete content, `class-wp-rest-users-controller.php:935`), so this is a UI omission, not an API limit. **Consequence:** an admin deleting an ex-author cannot give that author's posts to the replacement author from this screen — they get dumped on the admin. There is also no "delete all content" path.

2. **Role column shows slugs, not translated names.**
   Classic resolves each role to its translated display name via `translate_user_role()` (`class-wp-users-list-table.php:658-666`). The shell joins the raw REST `roles` array (`src/apps/users/index.js:146`), so the cell reads `administrator, editor` rather than "Administrator, Editor", and is not localized. **Consequence:** non-English admins see English slugs; capitalization differs from every other screen.

3. **Name column shows display name, not first+last.**
   Classic renders `first_name last_name` (or an em-dash) in the Name column (`class-wp-users-list-table.php:573-592`). The shell uses REST `name` (=`display_name`) as the title field (`src/apps/users/index.js:50`, `app.json:30`). These are different values — a user whose display name is set to their nickname will show that, not their legal first/last name. **Consequence:** the Name column content silently disagrees with classic for any user whose display name ≠ "First Last".

4. **Role counts: one request per role vs a single aggregate.**
   Classic calls `count_users()` once and reads all per-role buckets plus `total_users` and the `none` bucket from one result (`class-wp-users-list-table.php:191-259`). The shell fires one `per_page=1&_fields=id` request *per role value* (`src/apps/_shared/dataviews/useEntityElementCounts.js:44-59`). **Consequence:** N extra HTTP round-trips on every list mount (6 for the default role set), and the shell never computes a "No role" count (it would need a separate `wp_get_users_with_no_role`-style query, which has no REST equivalent). Classic also suppresses counts entirely on large installs via `wp_is_large_user_count()` (`class-wp-users-list-table.php:179`); the shell does not mirror that guard, so on a >10k-user site it would still fire the per-role count storm.

5. **Self-delete guard surface differs (functionally equivalent).**
   Classic includes the current user in the confirm list but marks them un-deletable and skips them server-side (`users.php:373-381`). The shell filters the acting user out of the target set *before* the request and annotates the modal copy (`src/apps/users/index.js:166-203`). Same end result; the shell additionally disables the confirm button when the selection is self-only. No user-visible downside — listed for completeness.

## API & platform blockers

The hard parity blockers — what classic does that cannot be done through `@wordpress/core-data` / the REST API today. Each verified against live 7.0 source.

1. **Send password reset — no REST endpoint. `[upstream]`**
   Classic calls `retrieve_password( $user->user_login )` directly inside the `resetpassword` action (`wp-admin/users.php:266`); the bulk action and per-row action both route through it (`class-wp-users-list-table.php:284-287`, `502-508`). There is **no REST route** that triggers a password-reset email: a grep of `src/wp-includes/rest-api/endpoints/` for password/reset/lost routes returns only `WP_REST_Application_Passwords_Controller` (a different feature). `retrieve_password()` lives in `wp-includes/user.php` and is not exposed. **To close:** either an upstream `POST /wp/v2/users/{id}/password-reset` (or a core action endpoint), or a shell-side custom route (`POST /wp-admin-shell/v1/users/{id}/password-reset`) that calls `retrieve_password()` server-side. The screen spec already proposes the latter (`docs/screens/users.md:426`). Tag `[upstream]` for the canonical fix; `[shell]` is a viable stopgap.

2. **Sort by Username (login) — not in the REST orderby enum. `[upstream]`**
   The classic primary column is sortable by `login` and is the default sort (`class-wp-users-list-table.php:396`). The REST `orderby` enum is `{ id, include, name, registered_date, slug, include_slugs, email, url }` (`class-wp-rest-users-controller.php:1605-1616`); the internal mapping (`:306-316`) has no `login`/`username` key. `WP_User_Query` itself *can* order by `login`, but the controller doesn't expose it. **Consequence:** the shell cannot offer "sort by username" the way classic defaults to. `name` (=`display_name`) is the closest available. `[upstream]` — needs `login` added to the controller's `orderby` enum + mapping.

3. **Per-user post count — PHP-only, not in the REST user schema. `[upstream]`**
   The Posts column uses `count_many_users_posts()` (`class-wp-users-list-table.php:411`), and `count_users()`/`count_user_posts()`/`count_many_users_posts()` all live in `wp-includes/user.php:616/661/1337` with no REST exposure. The REST user schema (`class-wp-rest-users-controller.php:1399-1526`) has no post-count field. **Consequence:** the shell cannot show the Posts count or the "→ posts by this author" link without either (a) an upstream `post_count`/`counts` field on the user resource, or (b) N `GET /wp/v2/posts?author=ID&per_page=1` requests reading `X-WP-Total` per visible row (expensive, public-context only). Tag `[upstream]` for the field; a `[shell]` per-row count proxy is the fallback (`docs/screens/users.md:138`).

4. **Aggregate role counts — `count_users()` not exposed. `[upstream]`**
   Same root cause as the Posts gap: `count_users()` (`wp-includes/user.php:1337`) returns `{ total_users, avail_roles{role→n, none→n} }` in one call and has no REST endpoint. The shell's per-role-request workaround (blocker-adjacent, see divergence #4) approximates it for ordinary roles but cannot compute the **"No role" bucket** (needs `wp_get_users_with_no_role()`, also PHP-only) and does not honor the large-install suppression. **To close:** upstream `/wp/v2/users` could surface counts (e.g. a `?_counts=roles` mode or a sibling route), or a `[shell]` `/wp-admin-shell/v1/user-counts` proxy. `[upstream]` preferred.

5. **Welcome / "Send User Notification" email toggle — not in REST create schema. `[upstream]`**
   The single-site create form has a "Send the new user an email about their account" checkbox (`user-new.php:629-635`) honored by `edit_user()` → `wp_send_new_user_notifications()`. The REST create path (`WP_REST_Users_Controller::create_item`, `:581-709`) calls `wp_insert_user()` and has **no `send_user_notification` argument** in the item schema (`:1399-1526`). `wp_insert_user()` does not send the notification; only the admin form does. **Consequence:** a shell-built add-user flow via `POST /wp/v2/users` creates the account but cannot send the standard welcome/password-set email (or offer the toggle). `[upstream]` — needs a `send_user_notification` arg on the create endpoint (`docs/screens/users.md:446`).

6. **Multisite: DELETE is refused, and invite/remove are internal. `[upstream]`**
   `DELETE /wp/v2/users/{id}` returns HTTP 501 (`rest_cannot_delete`) on multisite (`class-wp-rest-users-controller.php:919-926`). The multisite **Add Existing User / invite** flow (`add_existing_user_to_blog`, `wpmu_signup_user`, `user-new.php:75-240`) and **Remove from site** (`remove_user_from_blog`, `users.php:489`) have no REST equivalents. **Consequence:** on a network install the shell can list users but cannot delete, invite, or remove them — the screen is effectively read-only there. The shell also has no multisite awareness to swap Delete→Remove or show the invite form. `[upstream]` for the endpoints; `[shell]` for the missing multisite-mode branching.

7. **"Change role to…" bulk dropdown — *not* a blocker.** ✅ doable today.
   Worth stating explicitly to avoid mis-filing: REST fully supports this. `PUT /wp/v2/users/{id}` with a body of only `{ id, roles }` requires just `promote_user` (the controller special-cases the roles-only update, `class-wp-rest-users-controller.php:734-743`), and `check_role_update` enforces the same self-demote guard classic does (`:1277-1287`). A bulk role change = N such PUTs via `saveEntityRecord`/batch. This is a **missing feature** (`[shell]`), not an API blocker.

8. **Add New User (single-site) — *not* a blocker (except the email toggle).** ✅ doable today.
   `POST /wp/v2/users` accepts `username` (required), `email` (required), `password` (required), `first_name`, `last_name`, `url`, `locale`, `roles`, `nickname`, `meta` (schema `:1399-1526`). Everything the single-site create form needs except the welcome-email toggle (blocker #5). **Missing feature**, `[shell]`.

9. **Avatar, mailto, View-posts link, multi-role filter — *not* blockers.** ✅ doable today.
   `avatar_urls` is in the schema when `show_avatars` is on (`:1529-1551`); `email` and the author `link` are present in edit context; `?roles=a,b` does OR-multi filtering (`role__in`, `:282`). All shell-side work. `[shell]`.

## DataViews / DataForms review

The app uses **DataViews** (no DataForm — there's no create/edit form here, which is itself the headline gap). Import path is correct: `@wordpress/dataviews/wp` (`src/apps/users/index.js:7`), per the documented `Minified React error #130` avoidance rule.

Usage is **idiomatic** and matches the shared entity-CRUD pattern:
- View/selection state via `useEntityDataView` with title-field dedup and screen-flip resync (`src/apps/_shared/dataviews/useEntityDataView.js`) — correct; `name` is the `titleField` and is correctly stripped from `view.fields`.
- Fields/actions compiled from the resolved spec via `buildFields`/`buildActions` with the `FIELD_LABELS`/`ACTION_LABELS` locale tables (`src/apps/users/index.js:22-31`, `152-264`) — matches the codified PostsApp prototype.
- The destructive modal is a `RenderModal` from `createBulkConfirmModal` (`src/apps/_shared/dataviews/createBulkConfirmModal.js`) with the self-delete guard riding `filterItems` and `isConfirmDisabled` — clean, re-entrancy-guarded (`isBusy`), `Promise.allSettled` for partial-failure tolerance. This is the strongest part of the app.
- `records !== null` Spinner gate before mounting DataViews (`:285`) — correctly avoids the false-empty flash documented in the project rules.

**Issues / fragility:**

1. **Latent bug — the `administrators` variant filter never applies.** The manifest's `administrators` variant declares its role filter with `operator: "isAny"` (`src/apps/users/app.json:48`), but the queryArgs mapper only handles `operator === 'is'` (`src/apps/users/index.js:101`). Any `isAny` filter is silently dropped from the REST query. Since DataViews' multi-value filters naturally emit `isAny`/`isAll`, a roles filter the *user* sets through the UI (rather than via the `is` default) may also be ignored. The mapper should handle `isAny`→`?roles=csv` (which the REST `role__in` mapping already supports). This is the one outright correctness defect in the app.

2. **No `enableSorting` declared on any field** (`app.json:34-39`), so sortability is DataViews-default for the declared types. That means the shell exposes a *different* sortable-column set than classic (which restricts to Username + Email). Not a misuse of DataViews, but it drifts from parity and from the classic contract. The roles/registered columns being sortable client-side can also mislead — REST can't sort by login (blocker #2) and requires `list_users` for email/registered sorts.

3. **Roles filter `elements` are not in the baseline manifest** (deliberate — role lists are site-dependent, `app.md:82`). Consequence: out of the box the roles filter renders with whatever the cascade/filter supplies; the count-augmentation (`elementCounts`) only decorates elements that exist. This is a defensible design choice but means the typed role dropdown depends on a shell override or a `wp_admin_shell_data_view_config_root_user` filter to populate live roles — otherwise the filter is thin.

No component limitation in `@wordpress/dataviews` itself blocks parity here. The gaps are (a) missing actions/columns the app never wired, and (b) the REST blockers above. DataViews' action model is fully capable of expressing "Change role to…" (as a bulk action with a `RenderModal` containing a role `<SelectControl>`) and "Send password reset" (a bulk action with a confirm modal) — both are blocked only by the missing role-change wiring and the password-reset REST gap, respectively, not by DataViews.

## Recommendations / future work

**P1 — correctness + high-value, mostly shell-side**

1. **Fix the `isAny` role-filter drop.** `[shell]` — `src/apps/users/index.js:100-104`. Handle `operator === 'isAny'` (and `'isAll'` if ever emitted) by mapping the value array to `args.roles = value.join(',')`. Without this the `administrators` variant and any multi-select role filter silently no-op. This is a bug, not a feature gap.
2. **Add the "Change role to…" bulk action.** `[shell]` — new bulk action in `app.json#dataView.actions` + a `RenderModal` with a role `<SelectControl>`; on confirm, `saveEntityRecord('root','user', { id, roles:[role] })` per target (or a `/batch/v1` call), with the same self-demote guard the REST endpoint enforces. Fully supported by REST today (controller:734-743). Highest-impact missing action.
3. **Build the Add New User flow (single-site).** `[shell]` — a `core:users-new` form app (DataForm or hand-rolled) posting to `POST /wp/v2/users`. The `users-new` screen + route already exist in `wp-admin-default.json:1011-1018` but mount nothing useful. Note the welcome-email toggle is blocked (P3/upstream).
4. **Render the avatar + make email a mailto + show translated role names.** `[shell]` — `src/apps/users/index.js:50-59,146`. `avatar_urls['48']` from REST into the username cell; `<a href="mailto:">` for email; map role slugs through a role-name table (or surface translated names via the dataView `roles` elements). Cheap parity wins.

**P2 — navigation + ext points, shell-side**

5. **Wire row navigation to an Edit User app + a "View posts" row action.** `[shell]` — the list has no way to reach the edit screen (`app.md:75`); add an edit route (the `users/{id}/edit` screen exists, `wp-admin-default.json:1023-1032`) and a `view` row action opening the REST `link` (author archive). Edit-user itself uses `PUT /wp/v2/users/{id}` (available).
6. **Bridge classic `user_row_actions` / `manage_users_custom_column` into the dataView spec.** `[shell]` — the `core:users.row-actions` slot is documented but unwired (`app.md:81`). Without a bridge, third-party plugins that add user row actions/columns (common) vanish in the shell. Mirror the classic-menu-bridge approach.
7. **Mirror `wp_is_large_user_count()` before firing per-role counts.** `[shell]` — `src/apps/_shared/dataviews/useEntityElementCounts.js`. On large installs, suppress the count requests (and ideally the role-count labels) to avoid a request storm, matching classic.

**P3 — needs upstream WP/REST work**

8. **Send password reset (bulk + per-row).** `[upstream]` preferred (a REST action endpoint wrapping `retrieve_password`); `[shell]` stopgap via a custom `/wp-admin-shell/v1/users/{id}/password-reset` route. No REST surface exists today (verified — only application-passwords controller). `docs/screens/users.md:426`.
9. **Per-user post count + the Posts column.** `[upstream]` — add a `post_count` (or counts) field to the user REST resource, or expose `count_many_users_posts()`. Shell fallback is per-row `?author=ID&per_page=1` count requests (public-context only). `class-wp-rest-users-controller.php` schema, `wp-includes/user.php:661`.
10. **Aggregate role counts + "No role" bucket.** `[upstream]` — expose `count_users()` / `wp_get_users_with_no_role()` via REST so the role views can be a true tab strip with one request. Shell fallback documented (`/wp-admin-shell/v1/user-counts`). `wp-includes/user.php:1337`.
11. **Sort by Username (login).** `[upstream]` — add `login`/`username` to the REST users `orderby` enum + mapping (`class-wp-rest-users-controller.php:1605-1616`, `:306-316`). Needed to match the classic default sort.
12. **`send_user_notification` on create + multisite invite/remove/delete endpoints.** `[upstream]` — add the notification arg to `POST /wp/v2/users` (`class-wp-rest-users-controller.php:581`); expose multisite add-existing-user / remove-from-site, and lift the multisite DELETE 501 (`:919-926`) or provide a network-user REST surface. Until then multisite Users is effectively read-only in the shell, and the shell needs multisite-mode branching (Delete→Remove, show invite form).

**Doc note:** `docs/screens/users.md` exists and is accurate; no screen-spec gap to file. The app's own `app.md:72-82` "Known limitations" already lists most of these — this audit confirms each against 7.0 source and re-classifies the password-reset, post-count, role-count, username-sort, welcome-email, and multisite items as genuine API blockers rather than mere TODOs.
