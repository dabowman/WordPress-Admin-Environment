# Parity: Comments (core:comments)

> Audited 2026-05-29 against WordPress 7.0 core. Shell app: `src/apps/comments/`. Classic counterpart: `wp-admin/edit-comments.php` + `wp-admin/comment.php` + `wp-admin/edit-form-comment.php` + `WP_Comments_List_Table` (`wp-admin/includes/class-wp-comments-list-table.php`) + `js/_enqueues/admin/edit-comments.js` (inline reply / quick edit).

## Verdict

**Major gaps.** The shell delivers a competent moderation *list* — approve / unapprove / spam / trash as bulk + row actions, search, a status filter with live per-status counts, sortable date, pagination — and the destructive paths are sound. But it omits four of classic Comments' day-to-day surfaces, and *none of the four is blocked by the REST API*: the signature **inline Reply box** (REST `POST /wp/v2/comments` with `parent`+`post`), **Quick Edit** (REST `PATCH` of `author_name`/`author_email`/`author_url`/`content`), the **full single-comment Edit screen** (every field is a writable REST field), and the **Author column's email / URL / IP-address rendering** (all in the `edit`-context REST schema, just not displayed). On top of the missing features, the bundled `wp-admin-default.json` shell previously **redeclared the `root/comment/_default` dataView triple with a leaner action set** that *dropped the `unapprove` action and added an inert `reply` action with no callback* — making the shipped default worse than the app's own baseline. **That redeclaration regression is now fixed**: the shell action set is re-synced to the app baseline (`approve` / `unapprove` / `spam` / `trash`, no inert `reply`), so only the feature gaps below remain. Almost every gap is shell-side and closeable today; the only genuine API blockers are minor (no `author_ip` *collection/filter* param; no first-class moderation-count aggregate; `restrict_manage_comments` / `comment_row_actions` extensibility hooks have no REST surface).

## Counterpart mapping

- **Classic screen(s):**
  - List: `wp-admin/edit-comments.php` powered by `WP_Comments_List_Table` (`wp-admin/includes/class-wp-comments-list-table.php`).
  - Bulk dispatch + Empty Spam / Empty Trash: `edit-comments.php:24-151` (`delete_all` → `$wpdb` query at `:35-42`).
  - Single moderate confirm + edit: `wp-admin/comment.php` (switch on `action`, `:55-386`); edit form partial `wp-admin/edit-form-comment.php`.
  - Inline Reply / Quick Edit UI: `js/_enqueues/admin/edit-comments.js` (`window.commentReply`, `:782-1255`); save endpoints are admin-ajax (`wp_ajax_replyto_comment` `wp-admin/includes/ajax-actions.php:1309`, `wp_ajax_edit_comment` `:1468`, `wp_ajax_dim_comment` `:982`).
- **REST / core-data surface the shell uses:**
  - `useEntityRecords('root','comment', queryArgs)` → `GET /wp/v2/comments` (`WP_REST_Comments_Controller::get_items`).
  - `saveEntityRecord('root','comment',{ id, status })` → `PUT/PATCH /wp/v2/comments/{id}` (`update_item`; status-only path routes through `handle_status_param`, `:928-938` + `:1822-1857`).
  - `deleteEntityRecord('root','comment', id)` (no `force`) → `DELETE /wp/v2/comments/{id}` (trash; `delete_item` `:1074-1095`).
  - Per-status counts: `useEntityElementCounts` fires `GET /wp/v2/comments?status={s}&per_page=1&_fields=id&context=edit`, reads `X-WP-Total`.
- **Project screen spec:** `docs/screens/comments.md` — present, Tier-2 full spec. (One factual drift to correct upstream — see "Functional divergences": the spec asserts at `:123` that "REST does not accept `status: 'any'` for comments"; in WP 7.0 it does. The shell relies on `status: 'any'` working, and it does.)

## Functional divergences

Behaviors present in both that work differently:

1. **Default shell action set — resolved (was a regression vs the app's own baseline).** `app.json#dataView._default.actions` (`src/apps/comments/app.json:45-50`) defines `approve / unapprove / spam / trash`. `wp-admin-default.json` previously **redeclared the same `root/comment/_default` triple** with actions `approve / spam / trash / reply` — **dropping `unapprove`** and adding an inert `reply`. Per the cascade rule (CLAUDE.md: "A shell that redeclares a `settings.dataViews` triple wins OUTRIGHT — partial redeclaration silently drops app-baseline keys"; enforced by `inject_app_baselines`), the shell's array is authoritative and the app baseline is **not** merged, so the regression shipped. **It is now fixed**: the shell redeclaration mirrors the baseline (`approve / unapprove / spam / trash`, no `reply`), so the default workspace can un-approve from the list and shows no dead Reply button. The app maps callbacks for `approve`/`unapprove`/`spam` and a modal for `trash` (`index.js:319-342`).

2. **Status views are a filter dropdown, not a tab strip.** Classic renders persistent `All | Mine | Pending | Approved | Spam | Trash` links with counts and an active state (`get_views`, list-table `:250-366`). The shell renders one `status` filter element with counts folded into labels (`buildFields` + `withElementCounts`, `buildFields.mjs:105-116`; renderer wiring `index.js:258-271`). Consequence: switching "views" is two clicks (open filter, pick value) instead of one, there's no always-visible count overview, and `Mine` doesn't exist.

3. **`status: 'any'` IS valid in REST 7.0 — the screen spec is wrong.** `docs/screens/comments.md:123` claims "REST does not accept `status: 'any'` for comments" and prescribes a two-request union workaround. In WP 7.0, `WP_Comment_Query` explicitly handles it: `// 'any' overrides other statuses` (`wp-includes/class-wp-comment-query.php:559-560`) drops the status clause entirely, and the REST `status` collection param has `sanitize_key` + `rest_validate_request_arg` but **no `enum`** (`controller :1778-1784`), so `'any'` passes through. The shell correctly uses `status:'any'` as its base (`index.js:135`). The divergence is in the *doc*, not the code — flag the spec for correction. (Caveat: `'any'` requires `context:'edit'` + `moderate_comments`, which the shell satisfies.)

4. **`note` comment type — silent behavior coupling (WP 6.9+).** The shell omits `type`, so REST applies its default `type:'comment'` (`controller :1786-1792`), and `WP_Comment_Query` excludes the new `note` type for `'comment'`/'all' unless explicitly asked (`class-wp-comment-query.php:773-781`). Net: the shell correctly hides notes and pings. But this relies on the REST default; if a future dataView override sets `type:'any'`/`'all'`, the list would start surfacing notes/pings. Worth an explicit `type:'comment'` in `queryArgs` to be defensive (currently absent — `index.js:124-152`).

5. **No Undo after trash / spam.** Classic appends an "Undo" link to the success notice (`edit-comments.php:339-372`). The shell fires a plain "Moved to trash." / "Marked as spam." snackbar (`index.js:311-313`, `:64-67`) with no undo path. The data to undo exists (untrash/unspam via status PATCH), so this is a UX omission, not a capability gap.

6. **Capability floor is stricter than classic's view gate.** Classic lets any `edit_posts` user open `edit-comments.php` (`:11`) and see comments on their own posts (with `moderate_comments` only gating bulk + non-approved statuses). The shell gates the entire screen on `moderate_comments` (app.json `:9-11`; shell `:887-890`). Consequence: an Author/Contributor-ish role with `edit_posts` but not `moderate_comments` gets **no Comments screen** in the shell, whereas in classic they'd get a reduced one. Matches the app's actual capability (it does cross-author moderation), but it's a narrower audience than wp-admin.

7. **Bulk-action menu is not view-contextual.** Classic tailors bulk verbs to the active view (`get_bulk_actions :375-409` — e.g. Trash view offers Restore + Delete Permanently, Spam view offers Not Spam + Delete). The shell exposes a fixed eligible set regardless of which status filter is active; there is no Restore/Not-Spam/Delete-Permanently bulk verb at all.

- **Inline Reply** → `POST /wp/v2/comments` with `post` (required, `create_item_permissions_check :581-597`) + `parent` (schema `:1595-1600`) + `content` + `status:'approved'`. Logged-in author defaults are auto-filled (`create_item :703-710`). Classic uses admin-ajax `replyto-comment` but REST is a clean equivalent.
- **Quick Edit** → `PATCH /wp/v2/comments/{id}` of `author_name` / `author_email` / `author_url` / `content` — all writable (schema `:1532-1545`, `:1554-1575`; `update_item` `:939-977`).
- **Full single-comment Edit** → all of the above **plus** `status` and `date`/`date_gmt` (writable, `:1576-1587`). `touch_time`'s date editing maps directly to `date`/`date_gmt`.
- **Author email / URL / IP / avatar display** → `author_email`, `author_url`, `author_ip` (all `context:'edit'`), `author_avatar_urls` (when `show_avatars`) — all in `prepare_item_for_response` (`:1163-1209`). The shell just doesn't request/render them.
- **Unspam / Untrash / Delete-Permanently** → `handle_status_param` supports `unspam`/`untrash` via status PATCH (`:1842-1850`); permanent delete via `DELETE …?force=true` (`delete_item :1064-1073`).
- **Comment-type (Pings) filter** → REST `type` collection param accepts `comment`/`pings` (`:1786-1792`; `WP_Comment_Query` maps `pings`→pingback+trackback).

## DataViews / DataForms review

The app uses **DataViews** (list only — no DataForm, because there's no edit/quick-edit surface yet). Usage is mostly idiomatic and rides the shared `src/apps/_shared/dataviews/*` scaffolding correctly, but there are two real API-contract problems and one cross-cutting dead-property pattern.

**Correct / idiomatic:**
- Import path is right: `import { DataViews } from '@wordpress/dataviews/wp'` (`index.js:8`) — matches the skill's #1 rule.
- Controlled-component contract honored: `view` + `onChangeView` owned via `useEntityDataView` (seed + resync + selection-reset + title-dedup, `useEntityDataView.js:33-68`); `selection` + `onChangeSelection` wired alongside `supportsBulk` actions (`index.js:368-380`) — satisfies the bulk-action rule.
- Server-side fetch pattern is correct: `view` → `queryArgs` `useMemo` → `useEntityRecords`, `paginationInfo` from REST headers (`index.js:124-159`, `:353-359`).
- Destructive confirm via `RenderModal` with `Promise.allSettled` + re-entry guard is a solid pattern (`createBulkConfirmModal.js`).
- Loading gate: renders `<Spinner/>` while `records===null` rather than trusting `isLoading` alone (`index.js:362-367`) — matches the "gate DataViews on records !== null" rule.

**Problems / anti-patterns:**
1. **Inert action violated the Action API (default shell) — resolved.** DataViews requires *"either `callback` OR `RenderModal` — never both, never neither"* (actions-api ref, Rule #1). The default shell previously declared a `reply` action that reached `buildActions` (`buildActions.js:31-58`) with no entry in `callbacks` or `modals`, so the compiled action had **neither** — a clickable, eligible action that did nothing. The `reply` action has been removed from the shell spec, clearing the violation; a real reply modal/callback in the app remains future work (Recommendations P2).
2. **`isDestructive` is a dead property in current DataViews.** The shared compiler sets `compiled.isDestructive = !!spec.isDestructive` (`buildActions.js:42`) and the specs declare `isDestructive:true` on spam/trash (`app.json:48-49`, shell `:436`,`:442`). Per the actions-api reference: *"`isDestructive` was removed from the Action API. Destructive intent should be communicated through flow … not via a property on the action itself."* So the property is silently ignored — spam/trash get no special treatment from DataViews itself (trash's confirm modal carries the destructive `DestructiveButton`, which is correct; spam fires immediately with no destructive cue). Cross-cutting across all six entity-CRUD apps; worth fixing centrally in `buildActions.js`.
3. **`isPrimary` actions would need an `icon` (latent).** `buildActions` resolves `icon` only when `spec.icon` is set (`:44`). Today no comment action is `isPrimary`, so this is latent — but Rule #2 ("Primary actions must have an `icon`") means any future `isPrimary` comment action without an icon would misbehave. Not currently triggered.
4. **Status count folded into the filter label is a workaround, not a primitive.** `withElementCounts` appends `" (12)"` to element labels (`buildFields.mjs:105-116`) because DataViews has no native count slot on filter elements. This is the sanest available approach, but it's why the shell can't reproduce the always-visible tab-strip counts — and it costs N extra REST round-trips. Acceptable; flagged as inherent.

**Should it use DataForm?** Yes — the three missing edit surfaces (Quick Edit, full Edit, and the Reply composer) are exactly what `DataForm` is for. The shared `src/apps/_shared/forms/EntityDataForm.js` + `useEntitySave.js` scaffolding (used by profile / taxonomy / settings panels) is the right substrate. Quick Edit = a compact `DataForm` over `author_name`/`author_email`/`author_url`/`content`; full Edit adds `status` + `date`. The app currently hand-rolls nothing in their place — the features are simply absent.
