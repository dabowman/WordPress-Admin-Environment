# Parity: Site Health (core:site-health)

> Audited 2026-05-29 against WordPress 7.0 core. Workspace app: `src/apps/site-health/`. Classic counterpart: `wp-admin/site-health.php` + `wp-admin/site-health-info.php` + `wp-admin/includes/class-wp-site-health.php` + `wp-admin/includes/class-wp-debug-data.php` + `wp-admin/js/site-health.js`.

## Verdict

**Major gaps** — with a structural component that is **Blocked by API**.

The workspace app is a thin runner for the **5 async REST tests** only. It is missing two entire surfaces of the classic screen: (1) the **~22 synchronous "direct" tests** that constitute the bulk of the Status tab (WordPress version, plugin/theme versions, PHP version & extensions, SQL server, scheduled events, file uploads, debug mode, persistent object cache, etc.), and (2) the **entire Info / debug-data tab** (WordPress / directories+sizes / themes / plugins / media / server / database / constants / filesystem permissions, plus copy-to-clipboard). It also drops the health-score donut, the Critical/Recommended/Passed grouping with live counts, per-test remediation actions, the HTTPS one-click migration, and the issue-count caching transient. The direct-test results and the full debug report have **no REST surface** — `WP_Site_Health::get_tests()` direct tests run server-side via `wp_localize_script` (`class-wp-site-health.php:131-147`) and `WP_Debug_Data::debug_data()` has no `register_rest_route` anywhere (`class-wp-debug-data.php` registers nothing). Closing those requires either a workspace-side custom REST endpoint wrapping the PHP classes, or falling back to the iframe.

## Counterpart mapping

- **Classic screen(s):**
  - Status tab: `wp-admin/site-health.php` (page workspace + Mustache template `tmpl-health-check-issue` at lines 302-320), driven by `wp-admin/js/site-health.js` and powered by `WP_Site_Health` (`wp-admin/includes/class-wp-site-health.php`). Auto-update sub-tests live in `WP_Site_Health_Auto_Updates` (`class-wp-site-health-auto-updates.php`).
  - Info tab: `wp-admin/site-health-info.php`, powered by `WP_Debug_Data` (`wp-admin/includes/class-wp-debug-data.php`).
  - There is **no list-table class** — Status is a `<script type="text/template">` Mustache template hydrated by jQuery; Info is a server-rendered accordion of `<table class="widefat striped health-check-table">`.
  - Dashboard widget: `wp_dashboard_site_health()` (`wp-admin/includes/dashboard.php:1973`), registered at `dashboard.php:68`.
  - Menu: Tools → Site Health submenu with a critical-count badge (`wp-admin/menu.php:365-395`).
- **REST / core-data surface the workspace app uses:**
  - `GET /wp-site-health/v1/tests/{id}` via `@wordpress/api-fetch` — one request per test id (`src/apps/site-health/index.js:59-61`). Registered in `WP_REST_Site_Health_Controller::register_routes()` (`class-wp-rest-site-health-controller.php:50-178`).
  - The app uses **no `@wordpress/core-data` entities** (Site Health is not an entity type).
- **Project screen spec:** `docs/screens/site-health.md` — present, Tier-2 full spec (22 KB). It already documents the major gaps in §15 and the REST blocker in §4 "REST gap: bulk debug data". (Minor drift in the spec's §4 test list: it lists `utf8mb4_support` and puts `page_cache` under `direct` — in 7.0 source `utf8mb4_support` is gone and `page_cache` is `async`. Worth a spec touch-up.)

## Functional divergences

Behaviors present in **both** that work differently:

1. **Failure severity is inverted.** Classic treats an unreachable async test as a **recommended** "A test is unavailable" item (`wp-admin/js/site-health.js:336-345`). The workspace catches the rejection and renders it as **`status: 'critical'`** with the raw `err.message` (`src/apps/site-health/index.js:66-74`). User-visible consequence: a transient network blip on, say, the loopback test reads as a *critical security/perf failure* in the workspace and would (if a score existed) tank the score, whereas classic downgrades it to a soft "couldn't run." It also surfaces a raw JS error string rather than the classic's URL + friendly description.

2. **The Authorization-header test is run without its probe header.** Classic sends `Authorization: Basic dXNlcjpwd2Q=` (`wp-admin/includes/class-wp-site-health.php:2975`, applied at `wp-admin/js/site-health.js:277`) — the whole point of the test is to see whether the server strips that header. The workspace calls the endpoint with no headers (`src/apps/site-health/index.js:59-61`), so the test's result is **unreliable**: the endpoint cannot observe the header it is supposed to be probing. This is a correctness bug, not just cosmetics.

3. **Parallel vs. serial execution.** Classic chains tests one at a time via `maybeRunNextAsyncTest()` `.always()` recursion (`wp-admin/js/site-health.js:256-326`) — deliberate, because loopback/HTTP tests can be heavy and concurrent loopbacks can deadlock thin servers. The workspace fires all five concurrently with `Promise.all` (`src/apps/site-health/index.js:56-77`). Faster, but on constrained hosts the concurrent loopback + dotorg + HTTPS probes can interfere; the serialized classic order is the safer pattern.

4. **Category badge collapsed into status.** Classic renders the server-supplied `badge` `{label,color}` (e.g. "Security"/red, "Performance"/blue) verbatim (`wp-admin/site-health.php:306-308`). The workspace ignores `res.badge` and re-derives a pill purely from `status` (`src/apps/site-health/index.js:29-44`), so the **category label is lost** and the color set is reduced from six (blue/orange/red/green/purple/gray) to three intents (success/warning/error).

5. **No stale-cache write-back.** Classic POSTs the final counts to the `health-check-site-status-result` transient so the dashboard widget and Tools-menu badge reflect the latest run (`wp-admin/js/site-health.js:235-242` → `wp-admin/includes/ajax-actions.php:5462-5469`). The workspace never writes this. Consequence: if a site uses the workspace as its primary admin, the dashboard "Site Health Status" widget and the menu critical-count bubble go stale/zero.

6. **Score semantics differ because the population differs.** Even setting aside the missing donut, the workspace's count line ("N good · N recommended · N critical") is computed over **5 async tests** (`src/apps/site-health/index.js:89-97`), whereas classic's score and counts span **all ~27 tests** (direct + async) (`wp-admin/js/site-health.js:194-199`). A site with PHP-version and SQL-version criticals (both *direct* tests) shows "0 critical" in the workspace.

**REST surfaces that DO exist and are NOT blockers (workspace just hasn't adopted them):**

- `GET /wp-site-health/v1/tests/{background-updates,loopback-requests,https-status,dotorg-communication,authorization-header,page-cache}` — all six async tests (`class-wp-rest-site-health-controller.php:50-177`). ## DataViews / DataForms review

**N/A.** Site Health is not a tabular/entity surface and the app correctly does **not** use DataViews or DataForm — it renders `@wordpress/ui` `Card`/`Badge`/`Stack`/`Text` (`src/apps/site-health/index.js:4-7`). DataViews would be the wrong tool here (no rows/columns/filters/sort; the data is a severity-grouped accordion of HTML descriptions). No misuse to report.

One related observation: the app uses raw `@wordpress/api-fetch` rather than `@wordpress/core-data` — which is **correct and expected**, since Site Health tests are not entity records (the project's "all data via core-data" rule explicitly exempts non-entity operations, and `apiFetch` is the right primitive here). No anti-pattern.

## Recommendations / future work

Prioritized. "workspace-side" = doable today in this repo; "upstream" = needs a WP core / REST change.

**P1 — correctness & the biggest missing surface**

1. **Fix the Authorization-header test probe.** Send the `Authorization: Basic dXNlcjpwd2Q=` header on that one request (mirror `class-wp-site-health.php:2975`). *Where:* `src/apps/site-health/index.js:56-61` — branch on `t.id === 'authorization-header'` and pass `headers`. *Workspace-side.* Without it the test result is wrong.
2. **Stop scoring failed tests as critical.** Match classic: a network failure should render as `recommended` "A test is unavailable" with a friendly description, not `critical` with a raw error. *Where:* `src/apps/site-health/index.js:66-74`. *Workspace-side.*
3. **Add a workspace REST wrapper for the direct tests + plugin tests (closes B1 + B7).** New endpoint `GET /wp-admin-workspaces/v1/site-health/tests` that `require_once`s the admin class, calls `WP_Site_Health::get_tests()` (which applies the `site_status_tests` filter, capturing plugin tests), runs each `direct` test's callback server-side, and returns the array. Cap floor `view_site_health_checks`. *Where:* new `includes/*-rest.php` controller + consume in `src/apps/site-health/index.js`. *Workspace-side* (no core change needed). This single endpoint unblocks ~22 missing tests **and** plugin extensibility, and makes the score meaningful.
4. **Render the score donut + Critical/Recommended/Passed grouping with live counts.** Once #3 lands, the population is complete; implement the classic formula (`site-health.js:194-199`) and the three severity sections with a collapsed "Passed tests" disclosure. *Where:* `src/apps/site-health/index.js`. *Workspace-side.*

**P2 — Info tab and remediation**

5. **Add a workspace REST wrapper for the debug report (closes B2 + B3).** `GET /wp-admin-workspaces/v1/site-health/info` returning `WP_Debug_Data::debug_data()` **and** `WP_Debug_Data::format($info, 'debug')` (the clipboard string).
