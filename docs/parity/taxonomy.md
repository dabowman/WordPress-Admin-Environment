# Parity: Categories, Tags & Taxonomies (core:taxonomy)

> Audited 2026-05-29 against WordPress 7.0 core. Workspace app: `src/apps/taxonomy/`. Classic counterpart: `wp-admin/edit-tags.php` (list + inline Add form), `wp-admin/term.php` + `wp-admin/edit-tag-form.php` (single Edit), `wp-admin/includes/class-wp-terms-list-table.php` (the list table). REST: `/wp/v2/categories`, `/wp/v2/tags`, per-taxonomy `/wp/v2/{rest_base}` (all `WP_REST_Terms_Controller`).

## Verdict

**Major gaps.** The workspace app is a competent flat-list term manager (search, sort, pagination, create/edit modal, bulk delete) but is missing the two defining features of the classic Categories/Tags screen — **hierarchical (parent-indented) display** and **a parent picker on add/edit** — so it is not usable for organizing a real category tree. It also omits Quick Edit, the count→posts drill-down link, View archive links, default-category protection, term reassignment on delete, and term-meta rendering. The **bundled `wp-admin-default.json` previously shipped the Tags screen with an empty DataView** (no `taxonomy.post_tag` triple was declared and the app baseline only binds to `category`), so the Tags table rendered **zero columns and zero row/bulk actions** — a shipping regression. **That is now fixed**: the workspace declares a complete `(taxonomy, post_tag)._default` triple mirroring the `category` baseline, so Tags renders identically to Categories. The remaining items below are missing features, not regressions. Most gaps are closeable workspace-side; the genuinely API-blocked items are narrow (term reassignment-on-delete, a specific default-category error code, and the .org category↔tag converter).

## Functional divergences

Behaviors present in both that work differently:

1. **Flat list vs. hierarchical tree (Categories).** Classic recurses the term hierarchy and renders parent-indented rows, printing ancestor rows for context even when a page starts mid-subtree (`class-wp-terms-list-table.php:_rows()` 274-330; indent via `column_name` `:386` `str_repeat('&#8212; ', $this->level)`). The workspace maps records to a flat array and **reads `parent` into the row but never uses it** (`src/apps/taxonomy/index.js:128`) — rows render flat in `name asc` order. Consequence: a category tree like `Jazz → Bebop → Big Band` shows as three sibling rows with no visual nesting; users can't see or comprehend hierarchy. This is the headline parity gap.

2. **Edit is a modal, not a navigable screen.** Classic Edit is a full URL-addressable screen (`term.php?taxonomy=…&tag_ID=…`, reached by 302 from `edit-tags.php?action=edit`, `edit-tags.php:151-164`). The workspace opens a `@wordpress/components` `Modal` (`index.js:254-282, 345-381`). Consequence: an open edit form is not deep-linkable, survives no refresh, has no browser-back, and the classic Delete-from-edit-form footer (`edit-tag-form.php:299-309`) is replaced by Cancel/Save only. The screen-spec recommended `#/taxonomy-{tax}/{id}` route (spec §10) is not implemented.

3. **Add is a modal toggle, not a split pane.** Classic always renders the Add form in `#col-left` beside the list (`edit-tags.php:383-614`). The workspace hides it behind a toolbar "Add new" button that opens the same edit modal (`index.js:221-229`). Consequence: no always-visible add affordance, no rapid sequential entry with focus-return-to-name (classic's `document.forms.addtag['tag-name'].focus()`, `edit-tags.php:691-694`).

4. **Description rendering: stripped plain text vs. sanitized HTML.** Classic `column_description` returns the raw (kses-sanitized) description HTML (`class-wp-terms-list-table.php:571-580`). The workspace runs `stripTags()` (`index.js:46-48, 68-70`), removing all markup. Consequence: descriptions with intentional `<em>`/links render as flattened text in the workspace list. (Defensible for a table cell, but a divergence.)

5. **Click-name target.** Classic `column_name` wraps the name in `<a class="row-title" href="{edit_link}">` (navigation, middle-click-new-tab works) (`:415-419`). The workspace renders a `<Button onClick>` that opens the modal (`index.js:58-65`) — not an anchor, so no middle-click/copy-link, and it's a same-pane modal rather than navigation.

6. **Per-row capability gating timing.** Classic hides the selection checkbox (`column_cb` returns `&nbsp;` without `delete_term`, `:362-377`) and omits Edit/Delete row actions per `current_user_can` (`:478-521`). The workspace shows the Add button and Delete action unconditionally and relies on REST 401/403 to reject — the user discovers they can't act only after attempting it. Bulk delete additionally fires per-item DELETEs and reports failures after the fact (`createBulkConfirmModal.js:99-121`).

## API & platform blockers

The hard items — what classic does that the workspace cannot do through REST/core-data as-is. Verified against live 7.0 source.

1. **Term Quick Edit (inline name+slug save).** Classic ships an inline editor backed by the `inline-save-tax` admin-ajax action (`class-wp-terms-list-table.php:inline_edit()` 675-753; the JS posts to `wp_ajax_inline_save_tax`). **The REST equivalent EXISTS** — `PUT /wp/v2/{rest_base}/{id}` with `{name, slug}` (`class-wp-rest-terms-controller.php:update_item` ~650-720). So Quick Edit is **NOT blocked** — it's a [workspace] feature gap: the workspace would build an inline-edit affordance (DataViews has no native inline-edit cell, so this is a custom row state) and `PUT` via core-data. Tag: **[workspace]**.

2. **Term reassignment on delete.** Classic's `wp_delete_term($id, $tax, $args)` accepts `$args['default']` to reassign a deleted term's posts to a chosen term (`wp-includes/taxonomy.php` `wp_delete_term` signature). **REST `delete_item` calls `wp_delete_term( $term->term_id, $term->taxonomy )` with NO args** (`class-wp-rest-terms-controller.php:792`) — there is no `reassign`/`default` parameter in the DELETE route schema (`:134-138` only exposes `force`). So the workspace **cannot** offer "reassign posts to another term before deleting." Posts fall to the taxonomy default by core's silent fallback. Tag: **[upstream]** — needs a `reassign`-style param on the terms DELETE controller.

3. **Default-category protection signal (specific).** `wp_delete_term` returns `0` (falsy) for the site default category (`wp-includes/taxonomy.php:2047-2049`) and for a custom taxonomy's `default_term` (`:2055-2059`). REST `delete_item` maps any falsy return to a **generic `rest_cannot_delete` 500 "The term cannot be deleted."** (`class-wp-rest-terms-controller.php:794-800`) — there is no distinct "this is the protected default" error code. Two sub-cases:
   - For **`category`**: the default IS knowable workspace-side — `default_category` is `register_setting`'d with `show_in_rest: true` (`wp-includes/option.php:2868-2876`), readable at `GET /wp/v2/settings`. The workspace can pre-badge and disable Delete on that row entirely client-side. Tag: **[workspace]**.
   - For **custom hierarchical taxonomies** with a `default_term`: the option is `default_term_{taxonomy}` and is **NOT registered for REST** (verified — no `register_setting`/`show_in_rest` for `default_term_*` anywhere in `wp-includes`). So the workspace cannot know which custom-tax term is protected and can only react to the opaque 500. Tag: **[upstream]** — `default_term_{taxonomy}` (or a `is_default`/`protected` flag on the term schema) needs REST exposure.

4. **Category ↔ Tag converter link.** Classic links to the converter when `current_user_can('import')` (`edit-tags.php:638-663`), targeting the `wpcat2tag-importer` plugin via `admin.php?import=wpcat2tag` or `import.php`. This is a **bundled-importer / admin-page** feature with **no REST surface**; the importer is not a core-data entity. Tag: **[upstream]** (and effectively out of scope — spec §16 excludes the converter). The workspace could at minimum link out to classic `import.php` via the admin-link interceptor.

5. **Count-column → filtered post list.** Classic links the count to `edit.php?{query_var}={slug}` (`column_posts:595-622`). **NOT blocked** — `/wp/v2/posts?categories={term_id}` / `?tags={term_id}` is fully supported (`class-wp-rest-posts-controller.php:prepare_tax_query` 3229-3294), and the terms controller even pre-builds the link in `_links['https://api.w.org/post_type']` as `?{rest_base}={term_id}` (`class-wp-rest-terms-controller.php:1017-1028`). Note REST filters by **term ID**, classic by **slug** — equivalent result. Tag: **[workspace]** — needs the count renderer to emit a router link AND the posts app to honor a `categories`/`tags` filter.

6. **Full-depth hierarchical parent options (`wp_dropdown_categories`).** Classic renders an indented `<select>` of every term (depth-unbounded), with "None" and `exclude_tree` cycle-prevention on edit (`edit-tag-form.php:180-195`). **NOT blocked at the data layer** — `GET /wp/v2/categories?per_page=100&parent=…` returns all terms with `parent`, enough to build the indented tree and exclude a subtree client-side. The only friction is the 100/page REST cap (`per_page` max), requiring pagination for >100-term taxonomies — a perf concern, not a hard block. Tag: **[workspace]**.

7. **Term meta rendering.** Classic surfaces `register_term_meta` fields via the `{taxonomy}_edit_form_fields` hook. **NOT blocked** — `meta` is in the term REST schema (`class-wp-rest-terms-controller.php:1116`, requires `show_in_rest` on the meta registration). Tag: **[workspace]** — render via the workspace's `settings.dataFields` collection mechanism.

**Net:** of the brief's flagged blockers — Quick Edit, post-count link, tag cloud, default-category protection, full-depth parent options — only **reassign-on-delete** and **custom-tax default-term exposure** are true upstream blockers; **default-category (for `category`)**, **count link**, **parent options**, and **Quick Edit** are all workspace-side; **tag cloud is not a feature of this classic screen at all**.

## DataViews / DataForms review

The app uses both DataViews (list) and DataForm (the modal form). Usage is **largely idiomatic** with two real concerns.

**Idiomatic / correct:**
- Controlled `view` state via the shared `useEntityDataView` hook (`src/apps/_shared/dataviews/useEntityDataView.js`), `onChangeView={setView}` (`index.js:241`) — textbook server-side pattern: `view` → REST `queryArgs` (`index.js:89-108`).
- Correct import path `@wordpress/dataviews/wp` (`index.js:5`) — avoids the `Minified React error #130` trap.
- `getItemId` provided (`index.js:250`); `selection`/`onChangeSelection` wired for bulk (`index.js:248-249`).
- Bulk delete via `RenderModal` (`createBulkConfirmModal.js`) with `Promise.allSettled` (`:99`) and a re-entry guard (`:53, 84-86`) — robust against partial failure and double-click.
- `context: 'edit'` on the query (`index.js:96`) so `description` is populated — matches the documented requirement.
- DataForm `onChange` correctly merges the partial back into local state (`index.js:359-361`), seeded once per modal open.
- FIELD_LABELS/ACTION_LABELS translation tables (`index.js:23-33`) follow the codified locale-recovery pattern.

**Concern 1 — empty-config degradation is silent and severe.** `buildFields(dataViewConfig.fields, …)` and `buildActions(dataViewConfig.actions, …)` both null-guard with `?? []` (`buildFields.mjs:37`, `buildActions.js:35`). That prevents a crash but means when a `(taxonomy, name)` triple resolves empty, DataViews renders with **zero fields and zero actions** — a blank table — with no error or fallback. This was the root cause of the now-fixed empty Tags screen (`post_tag` is now declared in the bundled workspace), but it still bites any custom taxonomy mounted without a declared triple. The app does not synthesize a minimal field set from the entity, so a misconfigured/missing dataView produces a silently broken screen. A defensive default (e.g. fall back to a built-in name/slug/count/description field set when `dataViewConfig.fields` is empty) would harden every taxonomy mount. Cite: `index.js:133-140`.

**Concern 2 — DataForm is under-used for the term form; the parent field is the gap.** The modal uses `DataForm` (`index.js:355-362`) but with only `name`/`slug`/`description` (`TERM_FIELDS` `:287-305`). DataForm natively supports the field types needed for a parent picker — there is no DataViews/DataForm *limitation* blocking it. A hierarchical parent could be a DataForm field of `type:'integer'` with async `elements` (the indented term list) and `isVisible` gated on `is_taxonomy_hierarchical`. So the parent-picker gap is a **workspace authoring gap, not a component limitation**. (Minor: the form is hand-wired with a separate Save button + local `isSaving` rather than `EntityDataForm`/`useEntitySave` from `src/apps/_shared/forms/` — defensible because the same modal serves both create and edit, but it diverges from the profile/term/settings convention and re-implements the save/notice flow.)

**Genuine component limitations that block parity:**
- **No native tree/indented row rendering in DataViews.** DataViews' table layout has no hierarchy/`aria-level` affordance, so the Categories tree can't be reproduced inside DataViews without either a custom name renderer that injects indentation by computed depth (data-side work) or rendering outside DataViews. This is the component-level reason the hierarchy gap is non-trivial.
- **No native inline-edit (Quick Edit) cell.** DataViews has no per-row inline-edit mode; Quick Edit would be a custom row-expansion state.
