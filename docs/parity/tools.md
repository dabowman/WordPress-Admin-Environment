# Parity: Tools — Import / Export / Privacy (core:tools)

> Audited 2026-05-29 against WordPress 7.0 core. Workspace app: src/apps/tools/. Classic counterpart: tools.php, import.php, export.php, export-personal-data.php, erase-personal-data.php.

## Verdict

**Blocked by API** (with a workspace-side wiring inconsistency on top).

The `core:tools` app is a static landing grid of five link cards — it does **not** reimplement any of the underlying tools. That is the only honest design choice available: Import is server-side admin code that runs importer plugins, Export streams a generated WXR file with **no REST endpoint at all**, and the personal-data export/erasure workflow is built on a non-`show_in_rest` post type (`user_request`) driven entirely by `admin-post`/`admin-ajax` + wp-cron. None of these four screens has a REST or core-data surface a native React app could consume, so the workspace falls back to wp-admin for all of them. The default workspace (`wp-admin-default.json`) wraps each in an `iframe:` screen, which preserves the chrome — but the landing app's own card buttons bypass those iframe screens and hard-navigate out of the workspace via `window.location.href`, so the iframe route only gets used via the left-nav menu, not via the landing cards. The lone native classic tool (the Category/Tag converter card on `tools.php`) is not represented at all.

## Counterpart mapping

- **Classic screen(s):**
  - `wp-admin/tools.php` — Available Tools. In 7.0 the only built-in content is the **Categories and Tags Converter** card (`tools.php:67-86`), itself just a link to `import.php`; everything else is whatever plugins hang on the `tool_box` action (`tools.php:93`).
  - `wp-admin/import.php` — importer list. Merges installed importers (`get_importers()`, `import.php:82`) with the WordPress.org popular-importers API (`wp_get_popular_importers()`, `import.php:38`); each row renders Install Now / Run Importer / Details actions wired to `update.php?action=install-plugin` + `plugins.php?action=activate` with per-action nonces (`import.php:114-224`). Importers are plugins that run server code; the Category/Tag converter is the `wpcat2tag-importer` plugin (`wp-admin/includes/import.php:192-195`).
  - `wp-admin/export.php` — Export. On `?download=true` it assembles `$args` from the content radio + filters and calls `export_wp( $args )` then `die()` (`export.php:64-125`), which **streams a WXR XML file** (`Content-Disposition: attachment`) via `wp-admin/includes/export.php` `export_wp()`. The form itself is a `method="get"` form with content scope radios + per-scope category/author/date-range/status dropdowns (`export.php:181-346`).
  - `wp-admin/export-personal-data.php` — privacy export requests. Renders `WP_Privacy_Data_Export_Requests_List_Table` + an "Add Data Export Request" form posting `action=add_export_personal_data_request` with the `personal-data-request` nonce (`export-personal-data.php:90,113-144`). Lifecycle handled by `_wp_personal_data_handle_actions()` (`wp-admin/includes/privacy-tools.php:73`), `wp_create_user_request()` / `wp_send_user_request()` (`wp-includes/user.php:4775,4872`); the actual export bake runs async via the `wp_ajax_wp_privacy_export_personal_data` handler (`wp-admin/includes/ajax-actions.php:4937`).
  - `wp-admin/erase-personal-data.php` — privacy erasure requests. Same pattern with `WP_Privacy_Data_Removal_Requests_List_Table`, `action=add_remove_personal_data_request`, and the `wp_ajax_wp_privacy_erase_personal_data` handler (`erase-personal-data.php:90,142`; `ajax-actions.php:5127`).
  - Both privacy screens are backed by the **`user_request` post type**, registered `public => false` with **no `show_in_rest`** (`wp-includes/post.php:284-301`).
  - Site Health also lives under Tools but is a separate app — see `docs/parity/site-health.md`.
- **REST / core-data surface the workspace app uses:** **None.** ToolsApp reads only `window.wpAdminWorkspaces.adminUrl` (`src/apps/tools/index.js:56-59`) to build legacy links and calls `navigate('site-health')` for the one native sibling. It performs no `@wordpress/core-data` or `@wordpress/api-fetch` calls. (Note: `class-wp-rest-edit-site-export-controller.php:35` exists but is the **site-editor template ZIP** export — unrelated to content WXR export.)
- **Project screen spec:** present — `docs/screens/tools.md` (Available Tools), `docs/screens/import.md`, `docs/screens/export.md`, `docs/screens/personal-data.md`. All four are Tier-2 specs; no parity doc previously existed.

## Functional divergences

1. **Landing cards bypass the in-workspace iframe screens.** The default workspace declares dedicated iframe screens at `/tools/import`, `/tools/export`, etc. (`wp-admin-default.json:1077-1124`, `app: "iframe:import.php"`), which keep the user inside the workspace chrome. But the `core:tools` landing app's own cards do **not** route to those screens — for any `legacy` entry it sets `window.location.href = adminUrl(tool.legacy)` (`src/apps/tools/index.js:108-115`), a full browser navigation **out of the workspace** to raw `/wp-admin/import.php`. So the same destination behaves two different ways depending on entry point: left-nav menu item → in-workspace iframe; landing card → hard reload out of workspace. The card should `navigate('import')` (the screen id) to use the iframe screen, mirroring how `site-health` is handled (`index.js:99-101`). This also violates the project's own rule that workspace links never use `window.location.assign`/`href` — they should be `<a href>` so the admin-link interceptor maps them (CLAUDE.md "Workspace links never bypass the admin-link interceptor").

2. **Tool inventory differs from classic.** wp-admin's `tools.php` shows the Category/Tag converter card + whatever plugins add via `tool_box`. The workspace shows a fixed five-card set (Site Health, Import, Export, Export PD, Erase PD) and omits the converter entirely (`index.js:8-54`). Site Health is surfaced as a Tools card in the workspace but in classic it is a sibling submenu, not a `tools.php` card.

3. **Landing-screen cap floor is looser than the tools it links to.** The `tools` screen requires only `edit_posts` (`wp-admin-default.json:1057-1060`), so a contributor sees the landing grid including Import/Export/Privacy cards they cannot actually use; classic never shows `tools.php` content for those tools without the specific cap. The per-tool iframe screens re-gate correctly, so a click lands on a `wp_die(403)` inside the iframe rather than the card being hidden.

4. **Erase-PD screen drops the `delete_users` AND-requirement.** Classic requires `erase_others_personal_data` **and** `delete_users` (`erase-personal-data.php:12`); the workspace screen lists only `erase_others_personal_data` (`wp-admin-default.json:1118-1120`). Workspace `permissions.capabilities` is OR-semantic, so even if both were listed it would be an OR, not the AND classic enforces. The iframe's own `wp_die` still enforces the AND server-side, so this is a menu-visibility divergence, not a security hole.

## API & platform blockers

These are the reason the app is a linker, not a reimplementation. All are real; none is fixable purely workspace-side.

| Surface | What's missing | Tag |
|---|---|---|
| **Content export (WXR)** | `export.php` calls `export_wp()` (`wp-admin/includes/export.php`) which **streams a generated XML file** with `Content-Disposition: attachment` and `die()`s (`export.php:123-124`). There is **no `register_rest_route` for content export** anywhere in core (grep confirms only the unrelated site-editor template-ZIP controller, `class-wp-rest-edit-site-export-controller.php:35`). A native app cannot request a WXR with filters and get a file back over REST. | **[upstream]** — needs a core REST endpoint (e.g. `POST /wp/v2/export`) that returns a download URL or streams WXR with auth. |
| **Importers** | Importers are **plugins that run server-side admin code**; `import.php` orchestrates plugin install/activate/run via `update.php`/`plugins.php` + Thickbox (`import.php:114-224`). There is no REST surface to list, install, or run an importer, and the import process itself (parsing a WXR/3rd-party file and writing records) has no API entry point. | **[upstream]** — would need both a REST importer-registry endpoint and a REST import-runner; large surface. Realistically iframe-only. |
| **Personal-data export request lifecycle** | Backed by the **`user_request` post type registered without `show_in_rest`** (`post.php:284-301`, `public => false`). Creation goes through `admin-post` (`add_export_personal_data_request`, `export-personal-data.php:142`) → `_wp_personal_data_handle_actions()` → `wp_create_user_request()`/`wp_send_user_request()` (`user.php:4775,4872`); the export zip is baked **asynchronously via admin-ajax** (`wp_ajax_wp_privacy_export_personal_data`, `ajax-actions.php:4937`) + the email-confirmation token flow. No REST CRUD for requests, no REST trigger for the bake. | **[upstream]** — needs either `show_in_rest` on `user_request` (with a custom controller for the confirm/bake/download steps) or a purpose-built `/wp/v2/privacy-requests` endpoint set. |
| **Personal-data erasure request lifecycle** | Same as above: `WP_Privacy_Data_Removal_Requests_List_Table`, `add_remove_personal_data_request` admin-post, and the async `wp_ajax_wp_privacy_erase_personal_data` eraser (`erase-personal-data.php:142`, `ajax-actions.php:5127`). No REST. | **[upstream]** — same fix as export requests. |
| **`tool_box` / importer extension hooks** | Plugins extend Tools via `do_action('tool_box')` (`tools.php:93`) and `update_management_pages`-style menu hooks. The workspace has no equivalent registry, so plugin-contributed tools never appear in `core:tools`. | **[workspace]** — add a `wp_admin_workspaces_register_tool` filter/registry (already flagged in `app.md:24` and `app.json` `static-tool-list` constraint). |
| **Landing card → in-workspace navigation** | The cards leave the workspace instead of using the existing iframe screens. | **[workspace]** — change `index.js:108-115` to `navigate('import')` / `<a href>` per screen id; the iframe screens already exist in `wp-admin-default.json`. |

## DataViews / DataForms review

**N/A for the `core:tools` app** — it is a static card grid with no list, no fields, no forms.

Worth noting for context: classic `export-personal-data.php` and `erase-personal-data.php` are genuine **`WP_List_Table` screens** (status views, search box, bulk actions, per-page screen option — `export-personal-data.php:147-161`). If the `user_request` post type ever gains `show_in_rest`, these two would be ideal DataViews rebuilds (status filter axis, bulk delete/resend actions, `mediaField`-less list). Until the [upstream] REST blocker is resolved, they cannot be DataViews-backed and remain iframe.

## Recommendations / future work

- **P1 — [workspace] Fix the landing-card navigation.** Route each `legacy` card to its in-workspace iframe screen (`navigate('import')` / `<a href="#/tools/import">`) instead of `window.location.href` (`src/apps/tools/index.js:108-115`). Today clicking a card hard-reloads out of the workspace even though `wp-admin-default.json:1077-1124` already defines iframe screens. This is a one-file change and removes a CLAUDE-rule violation (no `window.location.href` for workspace links).
- **P1 — [workspace] Align erase-PD screen capability + document the AND-gate limitation.** Classic requires `erase_others_personal_data` AND `delete_users` (`erase-personal-data.php:12`); workspace `permissions.capabilities` is OR-only and lists just the first (`wp-admin-default.json:1118-1120`). Add a note (cap is best-effort; iframe enforces the real AND server-side) and at minimum include both caps so menu visibility is closer to classic.
- **P2 — [workspace] Add the Category/Tag converter card + a `tool_box` bridge.** Restore the missing converter card (link to the import iframe) and add a `wp_admin_workspaces_register_tool` filter so plugins that hook `tool_box` can surface a card (`src/apps/tools/index.js:8-54`; gap noted in `app.md:21-24`).
- **P2 — [workspace] Tighten the landing screen cap floor.** `tools` screen is `edit_posts` (`wp-admin-default.json:1057`); consider gating individual cards by their underlying cap (`import`, `export`, `export_others_personal_data`, `erase_others_personal_data`) so contributors don't see cards they can't use.
- **P3 — [upstream] Pursue REST surfaces for Export + Privacy requests.** A `POST /wp/v2/export` returning a signed download URL, and `show_in_rest` (or a dedicated controller) on the `user_request` CPT, would let the workspace build native Export and Privacy-request screens (the latter as DataViews) and retire the iframes. Track as core feature requests; nothing actionable in this repo until they land.
- **P3 — [workspace] Per-screen help-tab surface.** All five classic screens ship contextual help (`tools.php:45-58`, etc.) that the workspace drops outside the iframe. Cross-cutting workspace gap, not tools-specific.
