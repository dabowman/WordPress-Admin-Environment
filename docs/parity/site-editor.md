# Parity: Site Editor (core:site-editor)

> Audited 2026-05-29 against WordPress 7.0 core. Workspace app: `src/apps/site-editor/`. Classic counterpart: `wp-admin/site-editor.php` + the `@wordpress/edit-site` SPA package.

## Verdict

**Minor gaps** (with one structural caveat).

The Site Editor is a full single-page application shipped as the `@wordpress/edit-site` package, bootstrapped by `site-editor.php`. The workspace does not — and realistically cannot — rebuild it natively in v2; instead `core:site-editor` is a one-line delegation to `IframeApp` pointing at `site-editor.php` (`src/apps/site-editor/index.js:32-35`). Because the iframe loads the *exact* code wp-admin runs, **the entire interactive surface — every hub sub-screen (Templates / Template Parts / Patterns / Styles / Navigation / Pages), the block-editing canvas, multi-entity save, zoom-out/pattern insertion, revisions, style variations, Cmd+K palette inside the frame — is at full parity by inheritance.** There are essentially no *feature* gaps inside the editor.

The gaps are all at the **integration seam**: (1) the workspace has no exit/back affordance because `takeover` mode hides the workspace chrome and the app renders no toolbar of its own (unlike the sibling `core:editor`); (2) there is no deep-linking — the workspace route always loads the hub, never `?p=/wp_template/{id}`; (3) dirty-state does not bridge, so an intra-workspace navigation while the editor has unsaved block changes is silently discarded; (4) the chrome-hide CSS hides edit-site's own header/sidebar/site-hub, which can break the in-frame hub navigation if those class names drift in a WP release (the documented fragility). None of these is a missing *capability* — every entity the editor touches (`wp_template`, `wp_template_part`, `wp_block`, `wp_navigation`, `wp_global_styles`) is fully exposed over REST, so a future native drill-down is feasible. They are integration debt the iframe approach trades for shipping speed. The only true platform blockers are the server-computed editor settings (`get_block_editor_settings()`) and the ZIP-streaming export endpoint, both of which a native mount (not the iframe) would have to solve.

## Functional divergences

Behaviors present in both that work differently:

1. **Exit affordance — sibling `core:editor` has one, `core:site-editor` does not.** The post-editor app renders an explicit toolbar with a "Back to list" `Button` above its iframe (`src/apps/editor/index.js:172-181`). The Site Editor app renders nothing of its own — it returns `<IframeApp .../>` directly (`src/apps/site-editor/index.js:34`). Combined with `mode:"takeover"` (`wp-admin-default.json:931`), which hides the workspace sidebar and toolbar (`engine.json:54-62`), there is **no workspace-provided way to leave the Site Editor** — the user depends on the iframe's own internal hub navigation or the browser back button. In wp-admin the persistent admin menu is always one click away; here it is hidden. *User-visible consequence:* a user who drills into a template can feel "trapped" with no visible route back to the rest of the admin.

2. **Routing direction is one-way.** wp-admin's Site Editor is a true SPA — its URL (`?p=/styles&section=/css`) is the full app state, shareable and refresh-stable (`site-editor.php:22-118` redirect normalizer; spec §10). In the workspace, the canonical workspace URL is always `#/site-editor` regardless of where the user is inside the frame; the frame mutates its *own* `?p=` independently (`iframe-fallback` never reads or writes the inner `?p=`). *Consequence:* refresh of the workspace returns to the editor hub, not the user's last location; the workspace URL cannot be shared to land someone on a specific template. The screen spec (`site-editor.md:308-322`) describes an aspirational bidirectional `postMessage` hash sync that is **not implemented**.

3. **Chrome-hide hides the editor's *own* navigation chrome, not just wp-admin chrome.** `CHROME_HIDE_CSS` (`src/apps/_shared/iframe/chromeHide.mjs:23-33`) intentionally hides `.edit-site-layout__sidebar-region`, `.edit-site-layout__sidebar`, `.edit-site-site-hub`, and `.edit-site-layout__header-container`, then forces `.edit-site-layout__canvas-container`/`__canvas` to `inset:0`. This is a deliberate "show only the canvas" decision so the editor looks embedded. *Consequence:* it removes the in-frame site-hub/back chrome — which compounds divergence #1 (now neither the workspace nor the frame shows an obvious exit when the canvas is full-bleed) and depends on those exact Gutenberg class names continuing to exist (see blockers). In wp-admin those regions are visible.

4. **Dirty-state semantics differ at the navigation boundary.** wp-admin's editor blocks `beforeunload` when there are unsaved edits. The workspace's iframe apps do not register `useDirtyState`, and intra-workspace navigation is a hash change, not a page unload — so `beforeunload` never fires for it (`iframe-fallback/app.md:33`). *Consequence:* leaving via a workspace menu click while mid-edit drops the changes without a prompt; leaving via browser navigation (close tab / back) still prompts, because that *is* an unload. The behavior is inconsistent depending on *how* the user leaves.

## API & platform blockers

The Site Editor's *list* surfaces are all REST-backed (templates / template-parts / blocks / navigation / global-styles / block-patterns — every controller verified present in 7.0, see Counterpart mapping). So the memory-note intent — a native drill-down of `core:posts` over `wp_template`/`wp_block`/`wp_navigation` plus a chrome-hidden Styles iframe — **is achievable for the list views with current APIs**. The hard blockers below apply only to a *native canvas mount* (replacing the iframe). The current iframe sidesteps all of them by running the real PHP page, which is precisely why it ships.

| # | What wp-admin does | Missing surface | Tag | Notes |
|---|---|---|---|---|
| B1 | Injects server-computed editor settings via `wp.editSite.initializeEditor("site-editor", $editor_settings)` | `get_block_editor_settings()` (`wp-includes/block-editor.php:490`) is a **server-only PHP function with no REST equivalent**. The workspace would re-run the same PHP. Spec §14 already proposes replacing `block_editor_settings_all` with a workspace-level registry. |
| B2 | Bootstraps server-registered block definitions inline: `wp.blocks.unstable__bootstrapServerSideBlockDefinitions(get_block_editor_server_block_settings())` and registers block-bindings sources inline (`site-editor.php:271-298`) | Server block *schemas* are pushed as an inline script, **not** read from a REST collection (`/wp/v2/block-types` exists but the editor specifically uses the inline bootstrap for back-compat-shaped data). The `__experimental`/`unstable__` private API surface is also not a stable contract. | [workspace] | A native mount must replicate the inline bootstrap PHP-side. The iframe gets it for free. |
| B3 | `block_editor_rest_api_preload($preload_paths, $context)` warms ~25 REST paths into the page (`site-editor.php:181-258`) | `block_editor_rest_api_preload()` / `rest_preload_api_request` is a PHP-time priming mechanism. | B4 | Theme export streams a ZIP file | `/wp-block-editor/v1/export` IS a REST route (`class-wp-rest-edit-site-export-controller.php:34-44`) but the handler does `header('Content-Type: application/zip'); readfile(); unlink()` (lines 86-91) — it returns a **binary body, not JSON**. `@wordpress/core-data` cannot model a file-download response; it needs `apiFetch` with a blob parser or a raw `window.location`/anchor download. | [workspace] | Reachable, but outside the entity/core-data model. | B6 | (Native-mount only) Five coexistence blockers documented in `src/apps/site-editor/index.js:6-25` | Not API gaps but architectural collisions a native mount creates: (a) `core/preferences` store namespace collision with `core:appearance` (which writes workspace user-prefs, `src/apps/appearance/index.js`); (b) edit-site's `core/commands` set double-registers against the workspace's `core:command-palette`; (c) `body.is-fullscreen-mode` CSS fights the workspace's chrome; (d) edit-site's internal hash router collides with the workspace's hash router; (e) `@wordpress/edit-site` is absent from the dep-extraction `BUNDLED_PACKAGES` list, so the global + editor-settings wiring is itself a milestone. | [workspace] | All five are workspace-side engineering, not upstream. Each is individually tractable; bundled they exceed the v2 calendar (per `site-editor.md:421-431`). |

**No genuine [upstream] blocker exists for the iframe approach.** The only thing missing upstream is a *clean REST/core-data shape for the editor-settings + block-bootstrap data* (B1/B2) — but WordPress core itself does not consume that data via REST either, so it is fair to call it [workspace] work to replicate, not an upstream defect.

## DataViews / DataForms review

**N/A for the workspace app.** `core:site-editor` renders an iframe and uses no DataViews or DataForm at the workspace layer (`src/apps/site-editor/index.js` imports only `IframeApp`). The list sub-screens *inside* the editor use DataViews, but that is the `@wordpress/edit-site` package's own usage running inside the frame, not the workspace's `_shared/dataviews/*` scaffolding — so there is nothing to assess for idiomatic-ness on the workspace side.

Worth noting for future work: **if** the list sub-screens (Templates / Patterns / Navigation) were ever surfaced natively in the workspace as a drill-down (the memory-note intent), they would be excellent candidates for the workspace's existing entity-CRUD DataViews scaffolding — `wp_template` / `wp_template_part` / `wp_block` / `wp_navigation` are all standard REST collections with the same shape the six existing list apps (posts/taxonomy/users/comments/plugins/themes) already consume. The Styles canvas and block-editing canvas would still need to remain iframed (no DataViews equivalent). That hybrid is the natural next step and is feasible today (see B-table: list APIs all present).

## Recommendations / future work

**P1 — Add a workspace-level exit affordance.** *What:* render a minimal toolbar above the iframe with a "Back" / breadcrumb control, mirroring `core:editor`'s pattern (`src/apps/editor/index.js:172-181`), OR relax the screen from `mode:"takeover"` to `mode:"focus"` so the workspace sidebar stays reachable. *Why:* `takeover` + no app toolbar = no visible way to leave the Site Editor; the chrome-hide CSS also hides the in-frame hub chrome, compounding it. *Where:* `src/apps/site-editor/index.js` (add toolbar) or `workspaces/wp-admin-default.json:931` (change mode). *Side:* workspace-only.

**P1 — Bridge dirty-state to prevent silent data loss.** *What:* have the chromeless bridge post the editor's `isEditedPostDirty()` (or `core/editor` `__unstableIsEditorReady` + dirty selector) up to the parent, and wire `useDirtyState(regionId, isDirty, {blocksNavigation:true})` in the site-editor app so the workspace's `NavigationGuard` prompts before an intra-workspace nav. *Why:* clicking a workspace menu item mid-edit currently discards unsaved blocks with no prompt (`iframe-fallback/app.md:33`); browser-level navigation prompts but workspace-level does not — inconsistent and lossy. *Where:* `includes/engines/core-desktop/chromeless-bridge.php` (new sub-system) + `src/apps/site-editor/index.js` + `src/runtime/dirty-state`. *Side:* workspace-only.

**P2 — Deep-linking + history sync.** *What:* let the screen accept a `config.url` that carries `?p=…` and add a `postMessage` channel so the inner `?p=` changes update the workspace hash (and vice-versa), per the spec's stated intent (`site-editor.md:308-322`). *Why:* workspace URLs are currently opaque (`/site-editor` only) — no shareable/bookmarkable deep links, refresh returns to the hub. *Where:* `workspaces/wp-admin-default.json:920` (screen `config`) + a new bridge sub-system + `iframe-fallback`/`site-editor` consumer. *Side:* workspace-only.

**P2 — Fix the documentation source-path drift.** *What:* update the `src/runtime/apps/SiteEditorApp.js` references to `src/apps/site-editor/index.js` across `docs/screens/site-editor.md` (lines 5, 416, 463), `site-editor-styles.md`, `site-editor-templates.md`, `src/apps/site-editor/app.json:36`, and `app.md`. Also reconcile CLAUDE.md's "7 bundled workspaces" with the 3 actually present (`workspaces/` has only `wp-admin-default.json`, `single-pane-demo.json`, `desktop-demo.json`; the spec also references a non-existent `workspaces/developer-workspace.json` at `site-editor.md:464`). *Why:* the canonical path no longer exists, making the specs misleading for anyone rebuilding. *Where:* docs only. *Side:* workspace-only (doc).

**P2 — Update the app.md "Permalinks may navigate the iframe out from under us" limitation.** *What:* the app.md (`src/apps/site-editor/app.md:29`) lists this as an open limitation, but the chromeless bridge (loaded unconditionally, `wp-admin-workspaces.php:138`) now intercepts in-frame admin links and routes/keeps them sensibly (`iframeBridge.mjs` + bridge sub-system 9). Frontend links inside the frame still navigate the frame in place by design. *Why:* the limitation is stale/overstated. *Where:* `src/apps/site-editor/app.md`. *Side:* workspace-only (doc).

**P3 — Harden the chrome-hide CSS against Gutenberg class drift.** *What:* the selectors `.edit-site-layout__sidebar-region` / `.edit-site-site-hub` / `.edit-site-layout__header-container` (`chromeHide.mjs:23-33`) are package-internal Gutenberg class names not guaranteed stable across releases; the file already carries a TODO. Add a post-upgrade smoke check (Style Book canvas + hub nav) and consider a more resilient strategy (e.g. only hiding the outer admin chrome and letting edit-site's own full-screen mode handle the rest). *Why:* if these classes rename in a WP release the editor either shows duplicate chrome or breaks its canvas layout. WP 7.0's edit-site package may already differ — could not verify the current class names because the package ships pre-built (`wp-includes/js/dist/edit-site.min.js`), not as readable source in `wordpress-develop`. *Where:* `src/apps/_shared/iframe/chromeHide.mjs`. *Side:* workspace-side, but tracking an [upstream] moving target.

**P3 — Surface theme export as a workspace command (optional).** *What:* expose `/wp-block-editor/v1/export` as a command-palette entry with blob-download handling (B4). *Why:* nice parity touch; today it's only reachable via the in-frame More-menu. *Where:* `workspaces/*.json` `commands[]` + a small download helper. *Side:* workspace-only.

**P3 — Native list-view drill-down (the long-term direction).** *What:* build native Templates / Template Parts / Patterns / Navigation list screens with the existing `_shared/dataviews/*` scaffolding, keeping only the editing canvas + Styles iframed (the memory-note `core:posts`-over-`wp_template` intent). *Why:* gives the workspace native list UX (its own DataViews, search, bulk actions, deep-linking) while the genuinely-hard canvas stays iframed. All required REST collections are confirmed present. *Where:* new `src/apps/*` + `workspaces/*` screens. *Side:* workspace-only (uses existing REST). This is the path that closes the integration gaps without paying the native-canvas blockers B1/B2/B5.
